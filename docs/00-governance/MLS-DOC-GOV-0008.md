## 4. 新阶段验证规则

### 4.1 历史证据与当前变更

P3 浏览器豁免、P4 单轮 P95 性能及修复前性能影响复用仅保留对应候选和获批变更的证据效力。修订后的 Windows AI 脚本未运行、支付/审计样本不足、旧登录 500 未归因继续披露；不声明原 M6 全量、P99、三轮重复、多浏览器或长期稳定性通过。

新变更按其对代码、配置、迁移、模型和用户操作的影响确定回归。仅在确认输入与影响一致后复用历史结果；性能路径变化或旧样本不足时另列实际测量需要，未执行保持未完成。新核心页面变化在 Windows 原生环境复验；WSL 负责权威源码与独立依赖的非 GUI 验证，需要内嵌浏览器时先通知用户切换 Windows。

### 4.2 新增功能的 TLA 形式化回归

新增功能包括增加可调用能力、业务状态转换、后台任务或对外协议语义。每项均须登记需求/设计与 TLA+ 模型的对应关系，更新受影响模型或给出明确抽象映射，并执行其安全不变量、类型约束、需求明确要求的活性及相关共享模型回归。仅复跑一个与新功能无对应关系的旧模型不能满足门禁；缺模型/配置/映射是待完成。

TLC 证据包含同一 PR 当前提交、模型及配置 SHA-256、工具版本、常量/状态边界、抽象假设、检查性质、完整运行结果及反例。真实不变量无违例且规定检查完成才可记通过；有限边界的穷举结论只在该边界成立。可达性负探针逐条单独运行，只有产生预期轨迹才能记该探针通过；其预期 violated 不得当作真实不变量失败，也不得泛化为任意非零退出可接受。有限终态死锁处理须在配置和假设中说明。

模型结果与实现回归分别登记：数据库提交、锁、回调、重复投递及故障恢复仍需相应真实 PostgreSQL/HTTP 证据。实现与模型不一致、未预期反例、工具失败、跳过或没有证据均不满足新增功能门禁。

### 4.3 CI 与同版本证据

新增功能的 PR 必须提供干净检出可获得的模型、配置及验证入口，CI 执行 TLA 回归并保留证据；原前端、后端、Compose、观测技术作业继续验证。检查必须对应 PR 当前提交，缺失、失败、取消、跳过和旧提交成功都不算当前通过。新增提交及合并冲突处置后重新检查受影响结果。

现有 verification 是本地忽略资产，不能默认随 fetch 到达 CI。其原始资产和输出继续保全；后续接合 PR 须明确可正常追踪的新模型/配置/工具版本和校验和/执行入口，并按仓库规则调整追踪范围，不对原本地目录强制加入 Git。本轮没有修改忽略规则、模型、运行脚本或 CI。

## 5. 完整 PR 流程与部署出口

1. 在 GitHub Issue 登记问题/新增功能、可判定预期、范围及风险，关联批准需求；维护原编号。功能恢复或需求改变按变更控制先得到对应批准。
2. 从核对过的开发基线创建 codex/ 工作分支，保全原工作树；提交实现、模型/配置、测试及必要文档。提交不包含私有环境、凭据或原始业务备份。
3. 对 whitecait/Mylibrary 的 main 创建真实 PR，关联 Issue；说明行为变化、TLA 映射/假设/结果、技术回归、迁移/恢复与已知限制。Draft 用于准备阶段，具备评审条件后转可评审。
4. 核对当前 PR 提交的 CI 实际运行，完成明确评审人的独立评审，处理发现并重新验证；单人项目可由用户承担评审，保留实际评审结论，不伪造 GitHub 审批或分支保护已配置。
5. 达到检查条件并有适用合并授权后，通过 PR 合并；新基线或冲突改变输入时重做影响核对。即便平台未强制，人工出口核对仍执行新阶段门禁。
6. 合并提交的 CI 实际通过后，构建/选择与该提交相符的候选镜像，记录提交与镜像摘要、配置版本、迁移版本。发布前明确备份和已验证的恢复路径；数据库迁移不能假定可随旧镜像自动回退。
7. 向已确定目标机部署，实际检查健康、角色、核心业务、日志及必要模型连接；保留发布、失败、恢复/回退与运行反馈。Issue 在实际结果达到约定后收口，后续缺陷进入下一次 PR。

此流程是获批执行规则，当前没有新 PR、远端 CI、合并或目标机部署完成结论。WSL/Windows local remote 保持 fetch-only，不能向它们 push。后续 GitHub push/PR/merge、release 和公网部署按已获授权与明确目标执行，本轮文档批准不预填这些动作。

越权、错误结算、重复借出、数据丢失或核心流程阻断时停止发布，修复并复验后处理；既有质量豁免和 E 的风险接受不能豁免这类问题。
