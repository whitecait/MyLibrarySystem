## 2026-10-01 当前适用范围与批准修订

lingzz 于 2026-10-01 明确批准 A–E，并追加新增功能 TLA 形式化回归、CI 验证及完整 PR 流程要求。本节与[限定范围交付与 DevOps 阶段规则](../00-governance/MLS-DOC-GOV-0008.md)共同限定当前适用内容；下文相冲突的范围、角色、状态和准入表述保留为原基线历史，其余约束继续有效。批准修订与执行验证分别登记。

事务原子性、统一锁序、提交时重读守卫和效果幂等继续适用于保留业务。日结逐日连续追平后保持隔离，ADMIN 受控重开；隔离期允许恢复所需的管理员重新登录，不放开普通业务写。关闭订单的权限及降权同键重放按当前身份重新校验；UUID 命名空间防止模拟器重启后的事件号与历史冲突。形式模型与真实 PG/HTTP 提交验证分别登记。

## 1. 事务边界（跨事务时序的提交边界）

| 业务链    | 事务范围（同一数据库事务）                | 事务外                              | 依据          |
| --------- | ----------------------------------------- | ----------------------------------- | ------------- |
| 归还      | 借阅结束＋副本迁移＋罚款形成＋Outbox 登记 | 审计失败记录（独立事务）；异步投递  | SC-Q2         |
| 预约/候补 | 事务建立＋绑定或入队（原子）＋Outbox      | 候补确认前的展示（无事实）          | RS-D4/D6      |
| 取书借出  | 借出＋副本 LENT＋Outbox                   | —                                   | PK-D4         |
| 闭馆批次  | 未到馆处理＋清点＋结算三阶段＋本轮事件    | 失败诊断/审计（独立事务）；重试调度 | SC-Q5         |
| 复核批准  | 批准记录＋目标受控变更＋Outbox            | 失败审计（独立事务）                | SC-Q9/RV-D4   |
| 订单关闭  | 关闭事实＋占用释放（同事务原子）          | 失败日志                            | SC-Q15/D3/D12 |
| 支付成功  | 结算＋订单 PAID＋占用释放＋Outbox         | 退款流程（独立业务）                | SC-Q15/D5     |

规则：任何"业务事实＋事件"必须同事务；失败审计永远独立提交（不随业务回滚丢弃）；用户等待路径不含异步投递（AT-0002 既有口径）。

## 2. 条件更新（CAS）与冲突结果规则

- 全部状态迁移＝条件更新：`UPDATE t SET state=:next, version=version+1, updated_at=now() WHERE id=:id AND state=:expected AND version=:version`；影响行数 0 → 返回 `MLS-CIRC-003`/相应冲突码（携带当前最新状态摘要），**不自动重试业务判定**；客户端按 BR-0045 以最新状态重新确认（AT-0015/AT-0030 口径）。
- 终态封闭由迁移白名单（应用层迁移表＋无以终态为源的迁移）保证，越终态写入即条件更新失败。
- 建单独占：条件插入依赖 `uq_payment_order_unreleased`（DD-0003），冲突返回 `MLS-PAY-001`。

## 3. 统一锁序与死锁预防

固定获取顺序：闭馆控制 →（书目）预约队列 → 借阅事务 → 副本 → 罚款/订单 → Outbox；同层按主键字典序。实现约束：

- 用例编排按上序访问；行锁来自条件更新与 `SELECT ... FOR UPDATE`（仅显式需要多读一致时使用，按同序）。
- 锁等待超时 3s（`lock_timeout`）；超时＝确定失败，按冲突结果规则返回，不做隐式重试。
- 用户可见路径无自动重试（错误即返回）；后台闭馆重试为有限次（默认 1 次，配置 `closing.retry-budget`）、固定原业务日（SC-Q7/Q8）。

## 4. 逻辑 T：已选择方案与机制验证

用户已选择逻辑提交边界（MLS-DEC-0028）。计划闭馆钟点触发隔离请求，隔离成功提交才是 T；T 可以晚于计划钟点。原固定墙钟保证与普通 SELECT 门控证明均不再作为实现依据，ClosingGateCounterexampleTest 保留其反例历史。

1. 普通写事务使用 READ COMMITTED，在首次业务读取之前对全馆控制行执行 `SELECT status,version FROM closing_control WHERE scope='GLOBAL' FOR SHARE NOWAIT`，状态须 OPEN/REOPENED；缺少控制行失败关闭。取得共享锁后，同一事务再普通读取 V4 的 closing_admission.draining；为 true 或缺少该行即失败关闭，为 false 才完成许可授予。共享锁必须覆盖业务写入与 Outbox 至最终 commit/rollback，禁止切换连接或在校验后释放锁。事务记录读到的 version 为本轮许可代数。
2. 隔离协调器先在独立短事务把 closing_admission.draining=true 并提交（DRAINING）；该表与已被共享锁锁住的控制行分离，能停止新许可而不等待旧事务。随后隔离事务按统一锁序对控制行 `FOR UPDATE`，等待旧共享许可事务提交/回滚后更新 ISOLATED、version+1 并提交；此 commit 为 T，闭馆取数在此后独立开始。锁等待超时或隔离事务失败只形成失败记录，不伪造 T 已发生；已提交的 draining 保持 true，后续有限重试/人工恢复接续隔离，不能错误恢复新许可；不在一个事务里等待自己持有的共享锁。
3. 普通请求遇 draining=true、独占锁已持有或 ISOLATED 即明确失败，不隐式排队到重新开放后继续执行；NOWAIT 冲突 SQLSTATE 55P03 对应 MLS-CIRC-002。全局门控及业务状态读取必须在同一事务，旧展示快照不能冒充本轮许可。
4. 恢复只在固定原业务日期批次完成后进行；补结路径还需 ADMIN 权限与重新检查最新到期范围。恢复事务独占控制行，核对所有应存在的到期批次已生成且成功（不能仅凭现存行无失败推定完整），在同一恢复事务内更新 REOPENED、version+1 并将 draining=false，一起提交；新事务重新申请许可，旧请求不自动重放。正常单日路径按 SC-Q6，补结路径按 SC-Q10。
5. 引导初始化必须在同一事务先建立唯一 GLOBAL 控制行及 admission 行；全量业务写入都遵守上述协议，否则数据库锁不能替绕过门控的写入提供保证。恢复命令、闭馆内部事务与独立失败审计按各自权限与事务规则执行，不通过普通写许可入口。

补充实证：仅 FOR UPDATE 等待不能保证新的兼容 FOR SHARE NOWAIT 失败；原候选在排空阶段仍发放新许可的反例已归档，独立 draining 标记修复该缺口。当前部署为单应用实例，全馆闭馆/恢复控制命令由同一串行协调器执行，重启按持久化 draining/control 事实恢复；多实例或多个协调器不属于本原型的已验证范围，不能仅凭上述行锁推定控制命令已全局串行。

`LogicalClosingGateTest` 使用真实 V1～V4 迁移和独立数据库，验证：观察 PostgreSQL 的真实锁等待后释放旧事务；隔离前后新请求不排队；普通回滚不残留；不完整批次阻止恢复、恢复后代数递增；控制行缺失失败关闭。它是 SQL 机制原型，不是 M5 全量流通实现；权限、日历范围生成与所有业务用例接入仍须在 M5 证明。TLC Closing 模型增加 DRAINING 和 AbortWrite，T 仅在 inFlight=0 时发生；有限安全模型不保证墙钟期限或无限故障下最终恢复。

## 5. 异常、冲突与恢复行为汇总（可执行规则）

| 情形             | 结果/返回                     | 重试                 | 恢复                                                                      |
| ---------------- | ----------------------------- | -------------------- | ------------------------------------------------------------------------- |
| CAS 影响 0 行    | 冲突码＋最新状态摘要          | 不自动               | 客户端按最新状态重新确认                                                  |
| 建单撞占用       | `MLS-PAY-001`                 | 不自动               | 按原订单继续办理                                                          |
| 锁等待超时       | 冲突码（同 CAS）              | 不自动（用户路径）   | 重新提交                                                                  |
| 闭馆批次失败     | 当日整体回滚＋独立审计        | 后台有限次（原日期） | 耗尽转人工；管理员开放（DD-0002 §2.5）                                    |
| 支付尝试超时     | 仅日志，订单不变（D2）        | 用户主动再次支付     | —                                                                         |
| 关闭执行失败     | `MLS-PAY-004`，占用保持（D4） | 用户/系统再发起      | —                                                                         |
| 迟到事件到终态   | 仅日志（D15 吸收）            | —                    | —                                                                         |
| 进程崩溃于事务中 | 数据库原子回滚                | —                    | 重启后按最新事实继续；Outbox 未提交事件随事务消失，已提交事件至少一次投递 |

## 2026-10-07 日结自动恢复与重开守卫批准修订

lingzz 于 2026-10-07 批准日结在启动时自检并补齐漏结，管理员重开作为后备处置。本节明确替代 §4.4 中“补结路径还需 ADMIN 权限”作为必经操作者的限制；自动结算追平后可由系统受控开放。管理员后备入口仍要求 ADMIN 权限，未扩大角色权限。

- 启动与午夜流程按业务日期顺序补结。全部应结日期成功后，系统自动尝试开放普通写入。已有 MANUAL 批次，或非 SUCCEEDED 批次的 attempts 大于全馆 retry_budget 时，均停止自动重试并保留隔离。
- 同一 ClosingModuleImpl 实例用同一监视器串行执行 closeBusinessDate 与 reopen。该协调只覆盖当前单应用实例；数据库控制行锁仍是重开时复核持久化范围的依据，不把 Java 监视器视为跨实例锁。
- 重开先保留并检查原请求日期：请求不得早于 first_business_date，且从基线到请求日期的批次须全部成功。事务随后锁定 GLOBAL closing_control 行，再用锁后业务时钟计算 max(请求日期, today−1)，复查至该最新到期日的完整连续范围。只有两次检查均通过，才能在同一事务更新 REOPENED、current_date、version 和 draining=false。拒绝时保持隔离并返回 MLS-CIRC-008。未来请求日期继续拒绝。
- 若进程在等待控制行锁时跨过午夜，事务按锁后时钟复查新增到期日。缺少新批次时，重开拒绝且 draining 仍为 true；调度器先检查业务日期是否推进，再处理拒绝结果，并继续补结新增日期。日期未推进的其他拒绝仍停止自动恢复。
- 开始排空由独立短事务先提交。闭馆请求的外层幂等事务之后即使回滚，也不能撤销 draining=true。`/api/v1/closing/runs` 的准入分支不锁定 closing_control 或 closing_admission 行；外层请求未持有这两行的准入锁，独立事务不会因此自阻塞。
- 闭馆业务批次失败事务独立回滚。失败次数、retry_budget 判定与 MANUAL/RETRYING 状态在另一个事务中整体提交。该失败事务使用独立传播，确保外层幂等请求能保存 MLS-CIRC-014 结果。

真实 PostgreSQL 回归检查预算边界、失败后的外层 UOW 回滚、业务与 Outbox 回滚、批次失败状态和排空标记独立保存、MANUAL 后调度器保持隔离、普通 AI 写入仍被拒绝，以及控制行锁等待后重新核对范围。有限模型不证明 PostgreSQL 控制行锁或 SQL 事务实现；其边界见[形式化验证映射与边界](../../formal/README.md)。
