## 1. 文档目的

本文件定义 MyLibrarySystem 全面返工后的需求分析阶段工作方式、文档组织、编号与追踪规则、任务流、评审门禁以及首轮需求边界。它不直接规定 API、数据库表、类、框架、部署拓扑或其他实现细节。

项目采用 V 模型组织设计与验证活动：

| 左侧设计阶段 | 设计对象                                 | 右侧验证阶段 |
| ------------ | ---------------------------------------- | ------------ |
| 需求分析     | 整个系统的目标、边界、业务行为和质量要求 | 验收测试     |
| 总体设计     | 系统架构及子系统划分                     | 系统测试     |
| 详细设计     | 构件、接口、数据与协作关系               | 集成测试     |
| 模块设计     | 类、函数、组件和内部逻辑                 | 单元测试     |

当前只开展需求分析阶段。总体设计、详细设计和模块设计可以建立目录入口，但不得提前写入尚未评审的设计结论。

## 2. 重构与权威原则

1. 原系统未经过完整工程化设计，本次从需求分析重新建立系统基线。
2. 旧文档仅作为归档证据和历史参考，不构成当前需求、接口、数据或验收契约。
3. 已有代码按新需求逐项评估，可直接复用、重构复用或弃用重写；代码现状不得反向定义新需求。
4. 旧测试只能帮助识别历史行为或建立特征测试，不能直接作为新系统的验收证据。
5. 需求分析阶段只描述用户可观察的业务能力、规则、信息、约束和质量目标，不泄漏实现设计。
6. 所有未批准事项进入 Open 问题登记册；不得用假设值填充需求基线。

### 3.2 治理规则

- `docs/README.md` 是工程文档的唯一入口。
- `01-requirements`、`02-overall-design`、`03-detailed-design`、`04-module-design` 分别与验收测试、系统测试、集成测试、单元测试配对。
- 当前阶段只建设治理文件、`01-requirements` 和归档区；后三阶段只建立入口和职责说明。
- 旧文档应整体归档，并保留原始来源路径、归档日期、历史用途和替代文档链接。
- 归档内容不得继续充当当前契约；引用归档材料时必须显式标注“历史参考”。
- 文档状态统一为 `Draft`、`In Review`、`Approved`、`Changed`、`Retired`。
- 只有 `Approved` 工件可以作为下一阶段的正式输入。
- 已批准内容变更时，必须记录原因、影响范围、受影响追踪项和重新评审结果。
- 根 README 只提供项目入口和当前阶段概览，不重复维护需求事实。
- G0 前必须确认根 README 与整个 `/docs` 可被 Git 跟踪、评审和随仓库交付。
- 文档中的“计划”“验收用例”和“执行报告”必须区分；没有执行证据时只能记录为“尚未执行”。

### 4.3 需求分析活动边界

本阶段决定：

- 系统建设目标及其服务对象；
- 首版范围内与范围外业务能力；
- 参与者、外部系统和系统边界；
- 正常、替代和异常业务流程；
- 系统级用例、原子化功能需求和独立业务规则；
- 概念信息及其生命周期；
- 可量化的非功能需求；
- 每项需求对应的系统验收条件。

本阶段不决定：

- API 路径、请求字段、响应字段和传输协议细节；
- 数据库表、索引、迁移脚本和存储产品；
- Controller、Service、Repository、前端组件或类函数结构；
- 框架选型、进程拓扑、容器编排和生产部署参数；
- 尚未评审的详细业务数值和技术实现方案。

## 5. 第三部分：编号与追踪规则

### 5.1 稳定编号

编号不得包含可能变化的子系统名称。

| 工件       | 编号格式            | 示例               |
| ---------- | ------------------- | ------------------ |
| 业务目标   | `MLS-OBJ-NNNN`      | `MLS-OBJ-0001`     |
| 参与者     | `MLS-ACT-NNNN`      | `MLS-ACT-0001`     |
| 用例       | `MLS-UC-NNNN`       | `MLS-UC-0001`      |
| 功能需求   | `MLS-FR-NNNN`       | `MLS-FR-0001`      |
| 业务规则   | `MLS-BR-NNNN`       | `MLS-BR-0001`      |
| 信息需求   | `MLS-IR-NNNN`       | `MLS-IR-0001`      |
| 非功能需求 | `MLS-NFR-类别-NNNN` | `MLS-NFR-SEC-0001` |
| 项目约束   | `MLS-CON-NNNN`      | `MLS-CON-0001`     |
| 验收条件   | `MLS-AC-NNNN`       | `MLS-AC-0001`      |
| 验收用例   | `MLS-AT-NNNN`       | `MLS-AT-0001`      |
| 决策记录   | `MLS-DEC-NNNN`      | `MLS-DEC-0001`     |
| Open 问题  | `MLS-OQ-NNNN`       | `MLS-OQ-0001`      |

ID 一经分配永久保留。废弃项改为 `Retired` 并保留变更原因，不得删除后复用编号。

### 5.2 单项需求必备字段

每条规范性需求至少包含：

- ID、标题和规范性陈述；
- 业务理由和需求来源；
- 相关参与者和业务域标签；
- 优先级：`Must`、`Should`、`Could`、`Won't this baseline`；
- 状态：`Draft`、`In Review`、`Approved`、`Changed`、`Retired`；
- 前置条件、依赖和相关业务规则；
- 一个或多个可观察、可判定的验收条件；
- 风险、版本和变更记录。

### 5.3 追踪链

需求阶段必须建立以下双向追踪：

```text
业务目标
  → 系统用例
    → 功能需求 / 业务规则 / 信息需求 / 非功能需求
      → 验收条件
        → 验收用例
```

后续阶段在不改变已有 ID 的前提下追加：

```text
需求 → 总体设计 → 系统测试
需求 → 详细设计 → 集成测试
需求 → 模块设计 → 单元测试
```

### 5.4 追踪控制

- 每项需求至少有一个来源和一个验收条件。
- 每个验收用例必须反向关联至少一项需求，禁止无来源测试。
- 每个业务目标必须由至少一个用例或需求实现。
- 旧代码和旧文档只能成为证据来源，不能成为唯一批准依据。
- 尚未创建的后续设计映射统一标记为 `Not created`，不得提前虚构。
- 修改已批准需求时，必须建立变更记录并重新评估关联的设计项和验收用例。
- 追踪矩阵必须能够识别孤立目标、孤立需求、缺失验收条件和无来源测试。

### 6.3 门禁定义

- **G0 治理就绪**：`/docs` 可被 Git 跟踪；旧资料已归档；模板、编号、状态和变更规则可用。
- **G1 范围评审**：系统目标、参与者、范围内外和外部系统明确；所有 P0 范围问题关闭。
- **G2 业务评审**：核心流程、异常流程、用例、功能需求和业务规则之间无关键冲突。
- **G3 需求质量评审**：所有 Must 需求原子化、无歧义、必要、可行且可验证，不包含未批准设计结论。
- **G4 验收就绪评审**：每项 Must 需求具有验收条件和验收用例；非功能需求具有量化阈值或正式批准的豁免。
- **G5 基线批准**：追踪矩阵无孤立项；评审问题已关闭或经批准延期；需求基线正式发布为 `v1.0`。

### 6.4 角色与责任

| 角色                  | 责任                                                     |
| --------------------- | -------------------------------------------------------- |
| 项目负责人/需求批准人 | 批准系统范围、业务规则和最终需求基线                     |
| 需求负责人            | 维护需求工件、Open 问题和追踪关系                        |
| 业务代表              | 从单一图书馆业务角度确认流程、规则和术语                 |
| 验收负责人            | 检查需求是否能转化为完整系统的验收场景                   |
| 架构与开发角色        | 提供可行性、风险和代码复用意见，不在需求阶段替代业务决策 |
| 配置管理员            | 维护文档版本、状态、变更记录和基线标签                   |

本项目为工程学习项目，同一人可以兼任多个角色，但每次评审必须分别记录编写、评审、批准责任，以保留工程过程证据。

### 6.5 需求分析退出条件

- 范围内与范围外能力均已批准；
- 关键参与者和外部系统全部识别；
- 所有 Must 需求具有来源、优先级和验收依据；
- 业务规则独立编号，不隐藏在用例叙述中；
- 非功能需求可测量，或具有正式批准的豁免；
- 需求与验收用例完成双向追踪；
- 文档不存在 API、数据表、类、框架等设计泄漏；
- P0 问题全部关闭，P1 问题具有批准结论；
- 需求基线完成签字确认并发布为 `v1.0`。

## 7. 第五部分：首轮需求边界基线

本节记录已确认的系统边界。具体需求条目仍需在专题登记册中编号、原子化并建立验收追踪。

### 7.1 已确认范围

| 主题     | 已确认边界                                                                                        |
| -------- | ------------------------------------------------------------------------------------------------- |
| 验收对象 | 整个系统，包括浏览器前端、后端、新数据库和完全本地的支付模拟器                                    |
| 服务组织 | 单一图书馆，不含分馆或多租户                                                                      |
| 系统角色 | 访客、读者、馆员、系统管理员                                                                      |
| 公开访问 | 访客可以公开检索馆藏                                                                              |
| 注册     | 用户可以自助注册，注册无需人工审核，成功后成为读者                                                |
| 首版业务 | 账户与权限、读者管理、馆藏管理、检索、借阅、归还、续借、逾期罚款、模拟支付、操作审计              |
| 馆藏粒度 | “书目 + 实体副本”；一个书目可对应多册副本，流通对象为具体副本                                     |
| 流通办理 | 借阅和归还由馆员发起；读者可以发起自助续借                                                        |
| 自动处理 | 系统按业务配置自动处理和筛选，边界项转交人工处理                                                  |
| 人工例外 | 馆员可以对边界项例外处理；必须记录原判定、原因、说明、操作人员和时间，高风险例外复核范围保持 Open |
| 政策粒度 | 首版采用全馆统一的借阅、续借和罚款规则，不按读者类型或资料类型分层                                |
| 支付目标 | 演示创建、结果查询、异步回调、重复通知幂等、关闭订单、退款和日终对账的完整支付闭环                |
| 支付边界 | 只使用完全本地的支付模拟器；不得接入真实支付平台、官方沙箱或真实支付网络，不产生真实资金交易      |
| 外部系统 | 首版除本地支付模拟器外不接入其他外部系统                                                          |
| 兼容策略 | 不兼容旧拼音 API、旧字段和旧数据库，不提供兼容迁移                                                |

### 7.2 本地支付模拟器安全约束

以下约束用于确保工程学习不会触发真实资金行为：

- 仓库不实现生产支付适配器；
- 不保存真实商户号、真实密钥、真实付款凭据或真实付款信息；
- 支付模拟器只允许本机或受控本地测试环境访问；
- 系统和测试环境不得向真实支付域名或官方支付沙箱发起请求；
- 自动检查应识别真实支付域名和疑似真实密钥；
- 用户界面必须显著标识“模拟支付，无真实资金交易”；
- 模拟器应支持成功、失败、取消、超时、重复回调、退款和对账差异等可控场景；
- 上述内容是系统约束，不在需求阶段指定模拟器的进程、协议或实现技术。

### 7.3 明确排除范围

- 多馆点、多机构租户和跨馆调拨；
- 电子资源管理；
- 预约排队和业务通知；
- 公告、留言、通用文件上传和统计仪表盘；
- 遗失、损坏与赔偿；
- 真实支付、官方支付沙箱和任何真实资金交易；
- 支付模拟器以外的外部系统集成，包括邮件、短信、统一身份认证和外部用户库；
- 旧拼音 API、旧字段、旧数据库及其兼容迁移；
- 将历史文档、历史测试或现有代码直接视为新需求。

### 7.4 代码与历史资产处理

| 资产                                                           | 初始处置原则                                           |
| -------------------------------------------------------------- | ------------------------------------------------------ |
| Maven、Vite 等工程骨架及通用开发工具                           | 优先评估直接复用或轻量调整                             |
| 后端认证、借阅、归还、续借、罚款实现                           | 仅作为重构复用候选，必须依据新需求重新评估             |
| 依赖旧拼音 API 和旧字段的前端业务 API 层及页面                 | 原则上重写，可按新契约复用非业务性展示资产             |
| `library-server/arc/**`                                        | 归档弃用，不进入新实现基线                             |
| 旧测试                                                         | 只作为历史业务示例或特征测试参考，不作为新系统验收证据 |
| 固定 JWT 密钥、数据库口令、开放式 CORS、自动更新生产表结构配置 | 必须废弃，不得继承到新基线                             |

具体复用结论必须记录在 `../evidence/MLS-DOC-EVD-0002.md`，并关联对应的新需求、风险和验证方式。

## 8. 首轮需求分析执行顺序

1. 完成 G0：使新文档权威链可被版本控制，建立归档与证据台账。
2. 将本文件中的已确认边界写入愿景、范围、参与者与上下文工件。
3. 逐项关闭影响范围和核心流程的 Open 问题。
4. 建立注册、公开检索、馆藏、借阅、归还、续借、罚款、模拟支付、人工例外和审计流程。
5. 从流程提取系统用例、功能需求、业务规则和信息需求。
6. 定义可测量非功能需求，并为批准的豁免留存理由。
7. 为每项 Must 需求建立验收条件和完整系统验收用例。
8. 执行追踪、质量和设计泄漏检查，完成 G1 至 G4。
9. 由需求批准人完成 G5 评审，发布需求基线 `v1.0`。
