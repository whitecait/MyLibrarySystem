本文定义系统验收策略草案。环境、数据、缺陷分级、准入和退出规则已由 `MLS-OQ-0014`（关闭，2026-08-20）批准，见第 4、6 节。

## 1. 验收对象

验收对象是完整系统，而非单独后端或既有代码：

- 用户使用的浏览器；
- 新系统前端；
- 新系统后端；
- 新数据库及本次验收形成的受控业务数据；
- 完全本地的支付模拟器；
- 系统管理的 AI 模型服务端点（本地模型部署或云端 API 形态按设计决策登记）。

这些部分共同支撑从用户操作到业务结果、持久业务事实、模拟支付结果、AI 交互记录和审计证据的端到端观察。任何单一模块测试、旧测试结果或文档检查均不能替代完整系统验收。

## 2. 验收范围

系统验收覆盖 `MLS-UC-0001` 至 `MLS-UC-0024` 的主流程、替代流程和异常流程，并验证：

- 四类业务参与者在批准权限范围内完成目标；
- 书目与实体副本、账户、流通、罚款、模拟支付和审计事实保持业务一致；
- 自动判定、边界项转人工和人工例外具有可观察结果与可追责证据；
- 读者预约与候补遵循已批准三线状态机口径：可预约守卫、闭馆结算与可用性刷新分配、失败判定唯一时点（次一开馆日＝预约日期的闭馆）、到馆与无需到馆通知、预约日取书借出校验、当日未到馆处理与副本清点重新入库；
- 读者页公共门户对未登录用户公开：顶部导航与搜索优先布局，检索、分类筛选、可借状态筛选、可在线阅读筛选、排序、分页、书目详情与公开在线阅读器（目录、翻页、页码跳转、缩放、全屏、书内搜索）均可未登录使用；门户仅按书目级展示`可借`／`不可借`，不展示副本数量、编号、位置与不可借内部原因；书目显示`可借`不代表请求必然获准，提交时仍按最新业务事实执行现行资格、队列与状态校验；
- 未登录用户触发预约或本人事务时打开登录模态框并固定展示提示`若无法登录，请线下前往服务台办理借阅。`，登录成功后继续原操作并按现行规则判定，放弃或失败不产生业务事实；
- “我的业务”提供当前借阅、预约与候补、历史记录三个分页页签，事务详情含当前状态、保证类型、预约日期与时段、通知记录与状态时间轴，仅本人可访问；
- 站内通知 Banner 展示未读业务通知中排序最高者（按关联预约日期临近程度排序、同日多条不另设先后；到馆与无需到馆通知对同一预约事务互斥，不同预约事务含同日不同书目的通知可并存），多条未读时显示`另有 N 条`并以卡片堆叠提示，点击进入事务详情，系统保留模拟短信或邮件发送记录（不接入真实短信或邮件通道）；
- 预约日历以颜色区分可直接确认、需要候补与不可预约，同一书目同一日期正常只呈现一种保证状态；候补提交前必须确认并展示固定说明`当图书收回时会进行通知，但不做其他保证。`；
- 自助借阅中心按“扫描读者证—连续扫描多册图书—分别校验—确认结果—清空会话”运行，混合成功／失败批次逐册呈现，失败不留持久事务记录；服务台借阅由馆员直接建立并填写读者与实体图书信息，读者不预先提交服务台请求；
- 读者预约必须填写取书时段，时段缺失不能完成预约；在线提交的预约日期最早为次一开馆日，服务台建立的当日预约不受此限；读者于预约当日提前、准时或延后到台取书均不因时段被拒；
- 首页到馆统计仅对馆员展示，四项计数（计划到馆、尚未到馆、今日借阅、明日预计到馆，含括号）在固定业务事实下按已批准口径形成唯一结果，并覆盖零数据、部分取消、借出失败转人工、跨日放行与无权限访问场景；
- 现场借阅（读者页面、服务台、自助中心批次）与预约借阅共用同一套自动校验，非候补借阅受候补队列守卫约束，明确拒绝不留持久事务记录；
- 模拟支付覆盖创建、查询、成功、失败、取消、超时、异步通知、重复通知幂等、关闭、全额退款、部分退款、日终对账和差异；
- 支付完全本地运行，不连接真实支付平台、官方沙箱或真实支付网络，不产生真实资金交易，也不保存真实支付凭据或付款信息；
- 用户在所有模拟支付交互中可显著识别“模拟支付，无真实资金交易”；
- AI 助手的问答与受确认辅助操作在角色权限过滤、确认执行、完整前后端校验和双日志关联边界内可观察、可判定；
- AI 验收以 Tool Calling 行为（工具选择、参数、确认流、入口卡片、日志关联）为主要判定口径，AI 自然语言回复内容仅作参考记录，不作为验收判定对象；
- AI 参与行为按已批准四级模型（L1 查询返回、L2 起草确认、L3 页面引导、L4 拒绝）与角色配置矩阵（含访客受限开放与 AI 调用额度池）执行并逐角色断言。

范围外能力、旧拼音 API、旧字段、旧数据库及兼容迁移不属于验收对象。

## 3. 需求准入

需求或验收用例只有同时满足以下条件才可进入执行候选集：

1. 关联需求、业务规则和信息需求处于已批准基线；
2. 关联验收条件具有明确、可观察、可判定的结果；
3. 影响执行边界的 Open 问题已经关闭并同步更新本工件；
4. 前置业务状态、数据类别、操作和证据要求已经批准；
5. 验收对象各部分具有可识别的基线版本；
6. 对应追踪关系不存在孤立需求、孤立验收条件或无来源测试。

## 4. 环境与数据原则

- 验收只使用受控本地环境和专用学习数据，不使用真实读者、真实商户或真实付款资料。
- 本地支付模拟器是验收对象的一部分，只产生受控模拟结果。
- 验收环境不得访问外部支付网络；网络出口证据应能证明零真实支付请求。
- 数据集必须可重复建立，能够区分正常、边界、冲突、重复与异常业务状态。
- 每次执行记录环境标识、系统基线、数据集版本和执行人，避免把不同批次的状态混合为同一证据。
- 验收环境与数据的最终组成、隔离级别和准入条件由 `MLS-OQ-0014` 批准：受控本地环境（浏览器 + 前端 + 后端 + 数据库 + 本地支付模拟器），隔离外部支付网络；使用专用学习数据、可重复建立的数据集，覆盖正常/边界/冲突/重复/异常状态。数据库为 PostgreSQL：集成层与系统验收环境的数据库口径依[全局开发计划](../../00-governance/MLS-DOC-GOV-0006.md) §4.5/§6.2 执行（集成层必须真实 PostgreSQL，H2 结果不可替代）。

## 5. 执行证据

每个验收用例至少保留：

- 执行批次、基线版本、环境标识和数据集；
- 参与者身份类别、前置业务状态与实际操作记录；
- 用户可观察的界面结果；
- 必要的业务事实、模拟结果与审计查询结果；
- 支付场景的本地边界、零真实支付网络调用和显著模拟提示证据；
- 预期与实际结果比较、缺陷引用、执行人、时间和复核人。

证据必须足以由另一名复核者重建判定过程。只保存“通过”字样而没有上下文，不构成系统验收证据。

## 6. 缺陷、退出与批准

缺陷分级、允许遗留缺陷、退出阈值和批准责任由 `MLS-OQ-0014`（关闭，2026-08-20）批准如下：

- **缺陷分级：** Sev-1 阻断核心流程/造成数据破坏/越权/真实支付风险/无法建立可信证据；Sev-2 使 Must 需求失败或造成关键业务事实错误；Sev-3 非核心功能或可替代性问题；Sev-4 文字/视觉或不影响业务判定的问题。
- **退出准则：** Sev-1 为 0；Sev-2 为 0；Sev-3 不超过 3 个且均有责任人、修复版本和批准的风险接受结论；Sev-4 可带缺陷退出但必须登记并评估对语言与无障碍验收的影响。
- **准入规则：** 需求及验收定义已批准（G5）、关联 OQ 已关闭或经批准延期、环境与数据集通过配置核对、所有用例具备可观察预期结果。
- **退出与批准：** 所有 Must 验收用例已执行、阻断项为 0、允许遗留缺陷均已批准、重测与回归范围已完成、证据可由另一复核者重建、最终结论由需求批准人签署。
